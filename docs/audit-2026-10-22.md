## Summary

The design is sound and well defended; the main risks are two parallel control
planes and documentation sprawl, not code defects. One clear chart bug was found
and fixed.

- **Scope:** docs versus code for the README, AGENTS.md, `docs/personal-hermes/*`,
  the manager and chart READMEs; spot reads of the Python runtime-manager,
  `agent_platform/`, the new Keycloak directory adapter, the manager chart
  template and its Dockerfile.
- **Not covered line by line:** most of the 19k source lines in `hermes-adapters`.
- **Decision taken after the audit:** this branch becomes a Rust-only personal
  Hermes rewrite. The Python runtime-manager and other legacy pieces are removed

## High-level design

The repo ships three systems through one Helm chart: the released v0.6.x
platform, the unreleased Rust personal-Hermes manager and the release machinery.

| Layer | What it is | State |
| --- | --- | --- |
| Released platform (v0.6.x) | Multica board backend (vendored upstream plus an auth patch), one shared Hermes Deployment, the Python `runtime-manager` that creates short-lived SSH worker Pods, a `tools` image for admin Jobs | Shipped; five images in v0.6.9 |
| Personal Hermes manager (Rust, v0.7.0 source) | `hermes-manager` with `api`, `controller`, `migrate` and `initialize` roles; `hermes-router-auth`; a Go/Yaegi Traefik plugin; a React dashboard. PostgreSQL is the only source of truth; the controller reconciles one Hermes per user in its own namespace, plus on-demand terminal workers | Large and tested in source; not released |
| Release machinery | `release-policy.json` lists every file allowed into each build context and the chart; privacy preflight; tag-only publishing; separate cache workflow | Mature |

The Rust manager is a durable reconciler:

- Each change records its intent in PostgreSQL before any Kubernetes call.
- Claims are leased with fencing tokens.
- Each created resource carries an HMAC-signed creation proof bound to its UID.
- Deletion completes only once absence is verified.

**Strengths**

- Security boundaries are enforced in code:
  - the API holds no Kubernetes token;
  - each instance has its own opaque execution credential;
  - the resolver requires mTLS with a verified certificate SAN;
  - administrator rights come from PostgreSQL grants rather than Keycloak roles.
- Crash recovery (intent journal, fencing, creation proofs, UID checks) is tested
  with real process kills.
- Build-input allowlisting and the privacy preflight are unusually rigorous.

## Design concerns

Four structural issues, none of them a bug today, each raising the cost of
future change.

1. **Two execution control planes.** The Python runtime-manager (SQLite, file
   config) and the Rust manager (PostgreSQL) do the same job with different
   models, and there is no adoption path between them. Every execution change
   has to be made twice. *Decision: remove the Python path on this branch.*
2. **The hexagonal split is mostly nominal.** `hermes-domain` has 439 source
   lines and `hermes-application` about 3.2k, while `hermes-adapters` has about
   19k. That one crate holds HTTP, OIDC, sessions, PostgreSQL, Kubernetes, the
   controller, admission and template validation. As a result, much of the policy
   logic lives in adapter and SQL code.
3. **No chart-to-binary contract test.** The chart builds the JSON config and the
   binary parses it with `deny_unknown_fields` plus its own runtime rules. The
   only bridge is a slow k3d fixture, and the fixed bug came from exactly this gap.
4. **Documentation sprawl.** There are 11 docs of about 3.7k lines under
   `docs/personal-hermes/`, several of them restating what is done and what is
   open, and they contradict each other (next section).

## Bugs fixed and verification

One bug was fixed: the manager chart made API-only mode impossible.

**Bug.** `templates/hermes-manager.yaml` always set `admin.uiDirectory`, but the
binary refuses to start with dashboard assets and no `admin.browser`. Any
API-only install would therefore crash-loop with a generic `Invalid` error. The
manager README says omitting browser config keeps the API usable.

**Fix.** The chart now sets `uiDirectory` only when `admin.browser` is present
and removes it otherwise. Regression test:
`test_manager_api_without_browser_sessions_stays_api_only`.

| Check | Result |
| --- | --- |
| `uv run pytest -q` | 191 passed |
| Ruff check and format | Pass |
| `helm lint charts/agent-platform` | Pass |
| Privacy preflight | Pass |
| `cargo fmt --check`, `cargo clippy -D warnings` | Pass |
| `cargo test` | Not run: needs the disposable PostgreSQL container |
| k3d and native acceptance fixtures | Not run |

Tooling note: `helm` is not on PATH, so `uv run pytest` fails until
`.local/dashboard-tooling/bin` is added. Document it, or make chart tests skip
with a clear message.

## Rust-only rewrite (done on this branch)

Scope: per-user Hermes commissioning and per-profile terminal backends, managed
by the Rust manager with its React dashboard and a lean Hermes plugin. Board
integration is deferred; the Multica backend stays as a standalone, disconnected
chart option.

| Component | Outcome |
| --- | --- |
| `services/hermes-manager`, `contracts/`, `plugins/hermes-route-resolver` | Kept. Worker spec no longer sets Multica checkout variables |
| `runtimes/hermes` | Kept for personal Pods. Removed Multica CLI and s6 services, the singleton cont-init hook, the conflicting `patch-terminal-scope.py` and the image-wide `/etc/hermes` overlay |
| `managed_execution` plugin | Personal-only. Connection comes solely from the manager's managed config; requests carry only contract fields; Multica task forwarding and runtime-manager defaults removed |
| `runtime-init.py` | Validates the effective managed backend and refreshes adapters; chart seeding and legacy migrations removed |
| `runtimes/agent-runtime` | Kept as the default worker; Multica CLI and checkout proxy removed, sshd is PID 1 |
| `services/runtime-manager`, `services/tools`, `tools/platform` | Removed |
| Legacy chart (shared Hermes, gateways, sandbox, bootstrap Jobs, optional services) | Removed; chart deploys manager roles plus the optional Multica board |
| Legacy examples and tests | Removed; release render uses `examples/manager` |
| Multica backend, `vendor/multica`, `services/multica` | Kept, not integrated |
